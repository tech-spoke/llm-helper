# フェーズ失敗時のエラーハンドリング監査

**調査日**: 2026-02-02
**対象**: `code_intel_server.py` の全 19 Step (submit_phase ハンドラ)

## 凡例

| 記号 | 意味 |
|------|------|
| OK | エラーを検知し、適切に報告（フェーズ遷移しない） |
| WARN | エラーを検知するが、対応に問題がある |
| BUG | エラーを無視して進める、またはユーザー介入が不足 |

---

## 共通バリデーション（submit_phase 呼び出し前）

| チェック | 処理 | 判定 |
|---------|------|------|
| `summary` 未指定/空文字 | `payload_mismatch` エラー返却、フェーズ遷移なし | OK |
| `tools_used` が list でない | `payload_mismatch` エラー返却、フェーズ遷移なし | OK |
| 必須ツール未使用（`session.tool_calls` で判定） | `payload_mismatch` エラー返却、フェーズ遷移なし | OK |
| EXPLORATION でツール 2 種未満 | `payload_mismatch` エラー返却、フェーズ遷移なし | OK |

> 共通バリデーションは `_validate_common_payload` + `_validate_tool_usage` で実装。
> submit_phase のディスパッチ前に実行されるため、全フェーズで有効。

## Step 別エラーハンドリング

### Step 2: BRANCH_INTERVENTION (`_submit_branch_intervention`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| `choice` が delete/merge/continue 以外 | `payload_mismatch` 返却 + 再選択指示 | OK |
| delete/merge 実行時に git 操作失敗 | `branch_operation_failed` 返却 + `requires_user_intervention: true` | OK (修正済み) |
| continue 時に `is_task_branch_checked_out` 失敗 | `except Exception: pass` で無視。フェーズ遷移は継続 | OK — `is_task_branch_checked_out` 自体が内部で try/except し安全な dict を返す設計。例外が外に漏れるのは git 未インストール等のプロセスレベル異常のみで、その場合は start_session 自体が成立しない |

### Step 3: DOCUMENT_RESEARCH (`_submit_document_research`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| `documents_reviewed` が空 | エラーなし。空リストで QUERY_FRAME へ遷移 | **BUG** — `no_doc=false` で DOCUMENT_RESEARCH に到達している以上、ドキュメント調査が求められている。instruction は「must_read を必ず読んで要約」と指示しているが、サーバーは空でも通す。空の場合は `payload_mismatch` で突き返し、調査を再実行させるべき |

> `no_doc=true` の場合はこのフェーズ自体がスキップされる（QUERY_FRAME へ直行）ため問題ない。

### Step 4: QUERY_FRAME (`_submit_query_frame`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| スロットが全て空 | エラーなし。空の QueryFrame で次フェーズへ遷移 | OK — instruction が「不明なスロットは空にし、推測はしないでください」と明記。`raw_query` は保持されるため後続フェーズで参照可能 |
| `_create_branch_for_ready` 失敗（fast_mode 時） | ブランチ作成失敗しても `branch_result` をレスポンスに含めるだけ。フェーズ遷移は継続 | **BUG** — 発生頻度は低いが、起きた場合はブランチなしで READY に入り PRE_COMMIT/MERGE で破綻する。失敗時はユーザー介入を求めるべき |

### Step 5: EXPLORATION (`_submit_exploration_v11`)

|-----------|------|------|
| `explored_files` / `findings` が空 | エラーなし。空データで Q1 へ遷移 | **BUG** — 共通バリデーション（tools_used/summary）はフェーズ固有フィールドの中身を検証しない。LLM が空で送ってきた場合は `payload_mismatch` で突き返すべき |

| 判定ロジックの失敗 | なし。`needs_more_information` の bool 値で分岐するだけ | OK — ゲートフェーズは単純分岐 |

### Step 8: Q2 (`_submit_q2`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|

### Step 9: VERIFICATION (`_submit_verification_v11`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| `hypotheses_verified` が空 | エラーなし。空リストで Q3 へ遷移 | **BUG** — 検証フェーズに入った以上、結果なしで通すべきでない。`payload_mismatch` で突き返すべき |
| 仮説に result=false が含まれる | エラーなし。そのまま進む | **BUG** — 未検証・否定された仮説が残ったまま READY に進むと実装品質が劣化する。全仮説 result=true が必要。1件でも false があれば VERIFICATION に留まり、仮説を再検証して再送するよう指示を返すべき |

### Step 10: Q3 (`_submit_q3`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| `_create_branch_for_ready` 失敗（IMPACT_ANALYSIS スキップ時） | ブランチ作成失敗してもフェーズ遷移は継続 | **BUG** — Step 4 と同じ問題。失敗時はユーザー介入を求めるべき |

### Step 11: IMPACT_ANALYSIS (`_submit_impact_analysis_v11`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| `impact_summary` が空 | エラーなし。空で READY へ遷移 | **BUG** — 影響分析フェーズに入った以上、結果なしで通すべきでない。`payload_mismatch` で突き返すべき |

> ブランチ作成は Q3 スキップ → READY パスでのみ実施。IMPACT_ANALYSIS → READY パスではブランチ作成呼び出しなし。

### Step 12: READY — タスク登録 (`session.register_tasks`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| フェーズが READY でない | `phase_mismatch` エラー | OK |
| タスクリストが空 | `empty_tasks` エラー | OK |
| タスク ID 重複 | `duplicate_task_ids` エラー | OK |
| pending タスクなし | `no_pending_tasks` エラー | OK |
| `register_tasks` がエラー返却 | エラー dict + READY_PLAN の `_phase_response` 返却 | OK |

### Step 13: READY — タスク完了 (`session.complete_task`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| フェーズが READY でない | `phase_mismatch` エラー | OK |
| タスク未登録 | `no_tasks` エラー | OK |
| 不明な task_id | `unknown_task` エラー | OK |
| 完了済みタスク | `already_completed` エラー | OK |
| 順序違反 | `wrong_order` エラー | OK |

### Step 14: READY — 全タスク完了 (`session.check_all_tasks_complete`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| タスク未登録 | `no_tasks_registered` エラー + READY_COMPLETE の `_phase_response` | OK |
| pending タスク残存 | `incomplete_tasks` エラー + READY_COMPLETE の `_phase_response` | OK |

### Step 15: POST_IMPL_VERIFY (`_submit_post_impl_verify`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| `passed=false`、failure_count < 3 | READY に差し戻し（再計画） | OK |
| `passed=false`、failure_count >= 3 | VERIFY_INTERVENTION へ遷移 | OK |
| `passed=false`、failure_count >= 3、`no_intervention=true` | READY に差し戻し（介入スキップ） | OK |

### Step 16: VERIFY_INTERVENTION (`_submit_verify_intervention`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| intervention_count >= 2 | `user_escalation: true` + user_escalation.md 参照指示 | OK |
| 介入後も失敗が繰り返される | failure_count リセット → READY 差し戻し。最大 intervention_count=2 で user_escalation | OK |

> **注意**: user_escalation 時もフェーズ遷移は行わない（VERIFY_INTERVENTION に留まる）。LLM がユーザーに相談した後、再度 submit_phase する想定。

### Step 17: PRE_COMMIT (`_submit_pre_commit`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| `commit_message` 空 | `missing_commit_message` エラー + PRE_COMMIT の `_phase_response` | OK |
| `branch_manager` 未取得 | `branch_manager_not_found` エラー返却 | **BUG** — `_phase_response` なし。Step 4/10 の `_create_branch_for_ready` 失敗が放置されたまま到達した場合に発生し得る（PRE_COMMIT には `task_branch_enabled` ガードがない）。`_phase_response` + `requires_user_intervention: true` で対処すべき |
| `submit_pre_commit_review` 失敗 | エラー dict をそのまま返却 | **BUG** — `_phase_response` なし。実質的に発生するのは `decision="discard"` に `reason` 未指定の場合のみ（`session.py:2003`）。`_phase_response(PRE_COMMIT)` を付けて reason 付きで再送するよう指示すべき |
| `finalize` 失敗（git commit 失敗等） | `finalize_failed` エラー返却 | **BUG** — `_phase_response` なし。pre-commit hook 失敗や working tree 不整合など LLM の実装に起因して発生し得る。`_phase_response(PRE_COMMIT)` + `requires_user_intervention: true` でユーザー介入を求めるべき |

### Step 18: QUALITY_REVIEW (`_submit_quality_review_v11`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| issues あり、revert_count < max | commit 準備クリア → READY に差し戻し | OK |
| issues あり、revert_count >= max | `forced_completion: true` で MERGE へ（品質問題未解決のまま） | WARN — 意図的設計だが警告あり |
| issues なし、prepared commit の実行失敗 | `commit_result.success` が false でも `commit_hash=None` のまま MERGE へ遷移 | **BUG** — 正常フローでは発生しない（PRE_COMMIT で prepare 済みのコミットを実行するだけ）。pre-commit hook 失敗や working tree 不整合等の異常状態でのみ発生。MERGE へ遷移せず `requires_user_intervention: true` でユーザー介入を求めるべき |

### Step 19: MERGE (`_submit_merge`)

| 失敗ケース | 処理 | 判定 |
|-----------|------|------|
| task_branch 未使用 | `session_complete: true` で正常終了 | OK |
| quality_review 未完了 | `quality_review_required` エラー + QUALITY_REVIEW の `_phase_response` | OK |
| branch_manager 未取得 | `branch_manager_not_found` エラー返却 | **BUG** — `task_branch_enabled=True` かつ `task_branch_name` 空という矛盾状態でのみ発生（通常到達不能）。起きた場合は `_phase_response` + `requires_user_intervention: true` でユーザー介入を求めるべき |
| `merge_to_base` 失敗 | `success: false` + エラーメッセージ返却 | **BUG** — `_phase_response` なし。マージ失敗はコンフリクト等の異常状態。`_phase_response(MERGE)` + `requires_user_intervention: true` でユーザー介入を求めるべき |

## パターン分析

### エラー応答の形式パターン

サーバーのエラー応答は以下の 3 パターンに分かれる:

| パターン | 形式 | LLM のリカバリ可否 |
|---------|------|-----------------|
| A: 完全 | `error` + `message` + `_phase_response(現フェーズ)` | 可能 — instruction と expected_payload が返るため再試行可 |
| B: 不完全 | `error` + `message` のみ | 困難 — フェーズ情報がないため LLM が何をすべきか不明 |
| C: 無視 | エラーを検知せず `success: true` で次フェーズへ遷移 | 不可能 — 後続フェーズで予期しない状態になる |
